Aplikasi Kopi dan Nyemil

Aplikasi pemesanan kopi dan camilan untuk tugas UTS. Dibangun native Android dengan Kotlin, mengikuti wireframe delapan layar yang diberikan dosen, dengan tampilan yang dipoles agar lebih modern dan nyaman dipakai.

M. Ariel Davinsyah Putra · NIM 1247050122 · Kelas B · 9 November 2026 · Repo: putmarildav-stack/UTSArielDavinsyahPAM

1.Ringkasan Fitur

Untuk pembaca non-teknis: bagian ini menjawab "aplikasi ini untuk apa dan siapa yang butuh".

Masalah yang diselesaikan

Tugas kuliah meminta implementasi wireframe "Kopi dan Nyemil", sebuah aplikasi pemesanan minuman kopi dan camilan. Sebelum tugas ini, wireframe hanya berupa gambar sketsa di atas kertas. Setelah selesai, wireframe itu menjadi aplikasi Android yang bisa di-install, dibuka, dan dijalani alurnya dari awal (splash) sampai akhir (konfirmasi pesanan).

Cakupan fitur (8 layar sesuai ketentuan tugas)

  • Splash / Welcome dengan logo, tagline, dan tombol "Start now"
  • Sign Up (layar pilihan awal) dengan tombol Register dan Login
  • Login (username, password)
  • Register (nama lengkap, username, password)
  • Home: sapaan "Halo, [nama]", daftar 5 menu makanan/minuman, bottom navigation
  • Profile: ubah nama profil, tombol Save
  • Alamat Pengiriman (tab Order): nama lengkap, alamat, patokan, tombol "Order dan Kirim"
  • Konfirmasi Pesanan: pesan sukses, ringkasan alamat, tombol "Oke"

2.Keputusan Build dan Arsitektur

Setiap persimpangan keputusan di bawah sudah dikunci. Alasannya dicatat supaya keputusan tidak perlu diperdebatkan ulang di tengah pengerjaan.

PersimpanganKeputusanAlasan
Framework: Flutter vs Native Android Native Kotlin Materi kuliah PAM mengajarkan Android native (Kotlin, project "Empty Views Activity" di Android Studio). Pilihan lain (Flutter) sempat disiapkan lalu dibatalkan setelah dikonfirmasi ke pemilik tugas, supaya penilaian dosen tidak terganggu perbedaan teknologi.
UI: XML layout vs Jetpack Compose XML layout + ViewBinding Mengikuti gaya yang umum diajarkan di kelas (layout XML, Activity, Fragment). Compose adalah teknologi lebih baru yang belum tentu dipakai dosen di kelas.
Navigasi: banyak Activity vs satu Activity + Fragment Kombinasi Satu Activity per layar penuh (Splash, Signup, Login, Register, Konfirmasi) + satu MainActivity menampung 3 tab (Home, Order, Profile) lewat Fragment dan BottomNavigationView. Ini pola standar kuliah dan paling mudah dibaca dosen.
Data: database vs data statis Data statis (dummy) Ketentuan tugas menyatakan tidak perlu database. Data 5 menu disimpan dalam Kotlin object; data sesi pengguna (nama, alamat) disimpan di memori (object AppData) selama aplikasi hidup.
Gambar menu: file gambar vs emoji + gradasi warna Emoji + gradasi Tanpa file gambar binary, ukuran repo kecil, tidak ada isu lisensi foto, dan tetap tampak hidup. Wireframe aslinya memang hanya placeholder "Foto".
Versi SDK minSdk 26 · target/compile 36 SDK platform 36 tersedia di mesin kerja; minSdk 26 mencakup hampir semua ponsel aktif dan memungkinkan adaptive icon tanpa file PNG.
Bottom navigation Dipakai Wireframe menggambarnya, ketentuan tugas menyebutnya opsional tapi tidak melarang. Tab aktif diberi latar gelap ala "black pill" di wireframe.
Urutan kirim: push dulu baru tes build Push lebih dulu Instruksi eksplisit pemilik tugas: source code didorong ke GitHub sebelum uji build, agar pekerjaan tidak hilang kalau build bermasalah.

4.Peta Sistem dan Aktor

Aplikasi ini berdiri sendiri tanpa server dan tanpa database, jadi peta sistemnya sederhana: satu aktor (calon pemesan) berinteraksi dengan 8 layar yang berbagi satu data di memori.

flowchart LR User(["Pengguna (calon pemesan)"]) --> NAV["Navigasi layar"] subgraph APP["Aplikasi Kopi dan Nyemil"] NAV --> S1["Splash"] NAV --> S2["Signup"] NAV --> S3["Login"] NAV --> S4["Register"] NAV --> S5["Home (3 tab)"] NAV --> S8["Konfirmasi"] S5 --> S6["Tab Home: daftar menu"] S5 --> S7["Tab Order: alamat"] S5 --> S9["Tab Profile: nama"] end D1["AppData (memori): nama pengguna, alamat pesanan"] -.dibaca dan ditulis.- S5 D2["DummyData (statis): 5 item menu"] -.ditampilkan.- S6

Keterangan aktor dan komponen

  • Pengguna: mahasiswa/dosen yang menguji aplikasi. Tidak butuh akun sungguhan; login dan register menerima input apa pun yang tidak kosong karena tidak ada database.
  • AppData: penyimpanan sementara di memori. Menyimpan nama (dipakai di sapaan "Halo, [nama]") dan alamat pesanan terakhir. Hilang saat aplikasi ditutup total, wajar untuk aplikasi dummy.
  • DummyData: daftar tetap 5 menu: Kopi Susu Gula Aren Rp 22.000, Donat Cokelat Rp 12.000, Sourdough Loaf Rp 35.000, Cappuccino Rp 25.000, Matcha Latte Rp 27.000.

6.Skenario Negatif dan Edge Case

Aplikasi yang baik harus tahu diri saat pengguna mencoba hal yang tidak lengkap atau tidak wajar. Tabel ini adalah janji perilaku yang akan diuji satu per satu saat verifikasi.

#SituasiPerilaku yang diharapkanStatus rencana
1Login dengan username atau password kosongTombol tetap bisa ditekan, muncul pesan error di field kosong ("Username wajib diisi" / "Password wajib diisi"), tidak pindah layarDirancang
2Register dengan salah satu field kosongError inline di field kosong, akun tidak dibuat, tetap di layar RegisterDirancang
3Order dengan alamat kosong (nama, alamat, atau patokan)Error inline di field kosong, tidak lanjut ke konfirmasiDirancang
4Profile: nama dikosongkan lalu SaveError "Nama wajib diisi", nama lama tetap dipakaiDirancang
5Tekan tombol back di HomeKeluar dari aplikasi (Home adalah dasar tumpukan layar setelah login; layar login/register sudah dibersihkan dari back stack)Dirancang
6Tekan back di Konfirmasi PesananKembali ke aplikasi dengan tab Home aktif, bukan ke form alamat (form sudah selesai dipakai)Dirancang
7Nama sangat panjang (misal 60 karakter)Sapaan tetap rapi: teks bisa membungkus ke beberapa baris, layout tidak pecahDirancang
8Rotasi layar saat mengisi formInput yang sudah diketik tetap ada (disimpan otomatis oleh sistem), data sesi (nama) tetap aman karena disimpan di object terpisahAkan diperiksa saat verifikasi
9Aplikasi ditutup total lalu dibuka lagiData sesi kembali ke awal (contoh nama kembali ke nilai bawaan). Wajar untuk aplikasi dummy tanpa database; dicatat jelas di READMEKnown limitation

7.Titik Verifikasi Terbuka dan Langkah Berikutnya

Hal-hal yang belum bisa dipastikan saat brief ini ditulis, beserta rencana menutupnya. Tidak ada yang menghalangi implementasi.

  • Build APK pertama. Belum dijalankan saat brief ditulis. Rencana: gradlew assembleDebug dengan Gradle 9.1 (sudah ter-cache), AGP 8.13.2, Kotlin 2.3.21, JDK 17. Sesuai instruksi, source code didorong ke GitHub lebih dulu sebelum uji build.
  • Screenshot asli. Menunggu aplikasi jadi dan emulator berjalan (system image API 37 tersedia di mesin). Screenshot dipakai di README dan laporan pengujian.
  • Perilaku emulator headless di mesin ini. Akan dicoba saat sesi verifikasi; kalau emulator tidak mau hidup, verifikasi visual ditunda dan dilaporkan jujur, bukan diganti asumsi.
  • Pengumpulan tugas. Link repo dikirim sesuai format kelas. Repo sudah diset publik atas instruksi pemilik tugas.
